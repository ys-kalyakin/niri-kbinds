# Design: kbinds-mvp

## Context

Проект — зелёное поле: кода нет, есть SPEC.md (самодостаточное ТЗ, проверенные факты о целевой машине) и proposal.md со спеками четырёх capabilities. Целевая машина: Fedora 45, niri 26.04 (сессия активна), fuzzel 1.15.0, rustc/cargo 1.99.1 (rustup-прокси в песочнице сломаны — см. Risks). Живой конфиг: `~/.config/niri/config.kdl`, 144 бинда (эталон `grep -cE '^\s*Mod'` подтверждён), `include "./noctalia.kdl"`, 40 биндов с `Cyrillic_*`, живой конфликт `Mod+D` ×2.

Проверенные факты этой сессии (опора для решений):
- `niri msg action spawn -- <COMMAND>...` — подтверждён (`--help`).
- `niri msg action spawn-sh -- <COMMAND>` — подтверждён: принимает одну shell-строку.
- niri 26.04 парсит конфиг крейтом **knuffel 3.2.0** (niri-config/Cargo.toml), под капотом — `kdl` 2.x, т.е. диалект **KDL v1**.
- `xkbcli` на машине **отсутствует**; `/usr/include/X11/keysymdef.h` **есть** — эталон кириллической таблицы по процедуре §7.2 ТЗ.

## Goals / Non-Goals

**Goals:**
- Один статический бинарь `kbinds`, синхронный, без сети и рантайм-зависимостей.
- Логика парсинга/модели — в библиотечных модулях крейта (`lib.rs` + модули), тонкий `main.rs`; v2-оверлей переиспользует lib.
- Диалект парсера обязан читать живой конфиг; арбитр полноты — 144/144 (§7.3 ТЗ).

**Non-Goals:**
- Всё, что зафиксировано в proposal (GUI-оверлей v2, редактирование конфига, daemon, другие композиторы, vicinae-адаптер).
- Поддержка KDL v2 как целевого диалекта — целевой диалект определяется тем, что читает niri.

## Decisions

### D1. Парсер: крейт `kdl` в режиме KDL v1
niri 26.04 использует knuffel 3.2 → kdl 2.x → документы **KDL v1**. Берём крейт `kdl` последней мажорной (6.x) и парсим в режиме v1 (`parse_v1`), чтобы не тащить устаревшую мажорную версию ради диалекта. Альтернативы: knuffel 3.2 (тот же парсер, что у niri) — отклонён: derive-схема противится требованию «неизвестные свойства не роняют парсинг»; kdl 2.x напрямую — запасной вариант, если v1-режим свежего крейта не примет живой конфиг (см. Risks). Арбитр выбора — интеграционная проверка 144/144 на живом конфиге; обе версии закрывают её, берём свежую.

### D2. Выполнение действий — только через `niri msg action`
- `builtin` → `niri msg action <name> <аргументы…>`.
- `spawn` → `niri msg action spawn -- <argv…>` (синтаксис подтверждён).
- `spawn-sh` → `niri msg action spawn-sh -- "<строка>"` (подтверждён: один аргумент-shell-строка).
- Фолбэк, если маршрутизация через niri недоступна (niri msg не отвечает): прямой `std::process::Command` с `process_group(0)` и stdio в null, `#[cfg(unix)]` — как разрешает §8 ТЗ. Dry-run печатает итоговую команду (argv целиком) в stdout.
Альтернатива (всегда напрямую spawn) — отклонена: семантика niri (рабочий каталог, env) отличается, ТЗ требует маршрутизацию через niri.

### D3. Кириллическая таблица — только из keysymdef.h
`xkbcli` отсутствует, `/usr/include/X11/keysymdef.h` есть. При реализации: извлечь для 24 имён из §7.2 ТЗ (`a, be, de, el, em, er, es, ghe, ha, hardsign, i, ie, ka, o, sha, shcha, shorti, slash, tse, u, ve, yeru, yu, ze`) коды символов из keysymdef.h (формат `XK_Cyrillic_ve 0x0432`), зафиксировать `const`-таблицей в `normalize.rs`, юнит-тест на каждую пару «имя → символ». Проверка: `Cyrillic_ve → В`, `Cyrillic_a → А` (юникод U+0432/U+0430), свести выбранные символы с ручной выборкой из keysymdef.h при ревью. Неизвестное имя — сырое, без ошибки.

### D4. Идентификаторы биндов
`id` = kebab-case канонического combo (`mod+shift+w` → `mod-shift-w`; `+` → `-`, остальные символы combo уже безопасны). Дубли combo (легальны в конфиге — живой `Mod+D`) получают суффикс `-2`, `-3`… в порядке следования в модели — детерминированно между запусками. Модель строится как упорядоченный список, `exec` ищет по точному id.

### D5. Группировка и словарь титулов
Единая таблица в `groups.rs`: имя экшена → (русский титул, группа). Два уровня сопоставления: точное имя → затем префиксные правила (`focus-*` → «Навигация», `move-*`/`consume-*`/`expel-*` → «Окна», `workspace*` → «Воркспейсы», `screenshot*` → «Скриншоты», spawn с известными программами-лаунчерами → «Система»). Fallback: unknown builtin → группа «Прочее», титул = сырая запись; spawn → «Программы», титул = команда строкой. Таблица стартует из этих правил и выверяется на живом конфиге при реализации (там видны реальные 144 экшена); механизм детерминированный, словарь расширяем без изменения спеки.

### D6. dmenu-протокол и уникальность пунктов
`fuzzel --dmenu -p "binds> "`, пункты `<keys_display> — <title>` + имя действия. Пункт обязан быть уникальной строкой для обратного маппинга на id: при коллизии (возможна при одинаковых клавишах и одинаковых overlay-title у разных действий) к пункту добавляется различитель ` [<id>]`. Переносы строк в пунктах заменяются на пробел. Обратный маппинг: точное совпадение строки пункта → id → exec. Пустой stdout fuzzel (Esc) → выход 0 без действий. Точный код отмены fuzzel (пустой stdout vs код возврата) сверяется с документацией fuzzel 1.15 при реализации — ветка пустого stdout покрывает оба случая.

### D7. Ошибки и коды выхода
`anyhow::Result` наверху, `with_context` на IO/парсинге; без паник, без `unsafe`. `main` маппит: успех → 0; `--strict` с `error`-находками → 1; любая ошибка (IO/парсинг/usage/неизвестный id/fuzzel недоступен) → 2. Диагностика — stderr. Печать ошибок — `{:?}` через `anyhow`/`eprintln!`, без `unwrap` на пользовательском вводе.

### D8. Сборка и среда песочницы
Cargo.toml: package `niri-kbinds`, bin `kbinds`, `[lib]` + `[[bin]]`; deps: clap v4 (derive), kdl 6.x, serde (derive) + serde_json, anyhow. `cargo install --path .` → `~/.cargo/bin/kbinds`. В песочнице тулчейн вызывается напрямую: `export PATH="$(ls -d ~/.rustup/toolchains/*/bin | head -1):$PATH"` (проверено ТЗ §13: cargo 1.99.1 работает). Первая сборка требует доступ к crates.io.

### D9. Что делает `list` без `--json` (допущение)
ТЗ формат не специфицирует; принимаем: одна строка на бинд — `[группа] keys_display — title (id)`, отсортировано по группе и порядку в конфиге. Допущение зафиксировано, поведение не конфликтует со спекой (спека требует JSON только для `--json`).

## Risks / Trade-offs

- [kdl 6.x в режиме v1 может не принять живой конфиг (тонкости диалекта v1/v2)] → Арбитр — тест 144/144 на живом конфиге в первый же день работ; запасной план — откат на крейт `kdl` 2.x (диалект niri дословно), API почти идентичен для нашего подмножества чтения.
- [Дублированный combo в niri: семантика «победителя» не проверена] → A1 сознательно не называет победителя (требование спеки); задача чтения док/исходников niri стоит в tasks.md как исследовательская — влияет только на формулировку находки.
- [Таблица кириллицы, снятая вручную, может содержать ошибку] → источник — файл на диске (keysymdef.h), а не память; юнит-тест на каждую из 24 пар; сверка выборки при ревью.
- [Словарь групп неполон для 144 живых биндов] → fallback-группа «Прочее» и титул-из-сырой-записи гарантируют корректный вывод без паники; словарь расширяем без изменения спеки.
- [Сломанные rustup-прокси в песочнице] → обход D8 проверен в ТЗ; задачи не используют `cargo` без export PATH.
- [fuzzel-сценарий S1 требует живой сессии] → автотесты покрывают протокол (stdin/stdout), ручная проверка S1 — отдельная задача по DoD M3.

## Migration Plan

Не применим (новый компонент, нет обратной совместимости). Установка: `cargo install --path .` либо копия `target/release/kbinds` в `~/.local/bin`; бинд в niri — инструкцией из README (`Mod+Shift+Slash { spawn "kbinds" "dmenu"; }`). Откат — удаление бинаря.

## Open Questions

- Семантика niri при дублированном combo (чтение док/исходников) — только полировка формулировки A1, подход не меняет.
- Точные коды отмены fuzzel 1.15 — ветка пустого stdout уже покрывает поведение; уточнение косметическое.
- Vicinae API — исследовательская задача M5, исход (адаптер или «не поддерживается» в README) не блокирует MVP и не входит в этот change.
